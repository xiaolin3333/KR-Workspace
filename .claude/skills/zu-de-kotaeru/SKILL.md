# 図で答える（zu-de-kotaeru）

## これは何のためのスキルか

Claudeに何かを聞くと、たいてい「いちばん潰しの効く形」＝文章で返ってくる。長い文章は、読み終えても「なんとなくの雰囲気」しか残らないことが多い。
原因は読み手の理解力ではなく、返す形を指定していないこと。

このスキルは、**散文で返ってきそうな内容を、代わりに1枚のコンパクトな図として要求する**ための8つの定型プロンプトを提供する。
自分で読んで理解する場面と、人に報告・共有する場面の両方で使う。

出典と原典の考え方: HumanLayerの `show-me` スキル（"make your agent converse visually instead of in walls of prose"）を、
コーディング場面から報告・共有・研究/学芸業務の場面に翻訳したもの。

## 使い方の基本方針

1. これから書く・受け取る内容が、順番／関係／分かれ道／前後の差／経緯／比較のいずれかを含み、かつある程度の分量になりそうなら、
   いきなり文章で書き始めず、または長い回答をそのまま出さず、下の8パターンから合うものを選ぶ。
2. どれが合うか迷ったら、まず **パターン1（全体像マップ）** を先に出す。地図があれば、読む人（自分自身も含む）はどこを詳しく読むか選べる。
3. 各パターンのプロンプトは「そのまま送れる形」で書いてある。内容に合わせて主語や項目名だけ埋めればよい。
4. プロンプトには要素数の上限・文字数の上限を必ず含める。上限を書かないと、長い元の文章をそのまま図に詰め込もうとして、かえって読めない図になる。
5. 図を出した後は、必ず「これは人に見せる図か」を確認する（詳細は `references/post-processing.md`）。人に見せるなら整形チェックと、削られた例外の確認を行う。

## 前提条件（動かないときに確認すること）

- ネイティブな図（Artifacts上のダイアグラム）は **Claude の web版・デスクトップアプリのみ**。iOS/Android アプリでは描画されない。
- ターミナルの Claude Code では、この意味での図は出せない。文字で組んだ図（ASCII art的なもの）は返せるが崩れやすいので、HTML/SVGファイルを書き出してブラウザで開く方が確実。
- 出てこない場合は、画面左下の名前 → Settings → Capabilities → **Code execution and file creation** をオンにする。Freeプランでも使える。
- Team/Enterprise の場合は個人設定ではなく、Owner権限で Organization settings 側の Capabilities を有効化する必要がある。

## 8つのパターン

各パターンの「そのまま貼れる頼み方」は日本語で送ること。項目を埋める際も、元の文章の言葉をそのまま流し込まず、上限文字数に収まるよう言い換える。

### 1. 全体像マップ（自分が読む用）
**いつ使うか**: 長い回答が返ってきた／これから長い説明をする。全部読む前に、どこに何の話があるか先に知りたいとき。
```
本題に入る前に、この話の全体像だけを1枚の図にしてください。大きな塊を3〜5個、その下にぶら下がる項目は各3個までにして、階層が分かる形にしてください。中身の説明はまだ書かず、どこに何の話があるかだけ分かる地図にしてください。
```
地図が出たら「◯番目の塊だけ詳しく文章で書いて」と続けて、必要な部分だけ深掘りする。

### 2. 関係図（人に渡す用）
**いつ使うか**: 部署・人・システムをまたぐ話を整理したい。誰が誰に何を渡すのかを一目で見せたいとき。
```
登場する人・部署・システムを丸で、その間のやりとりを矢印にした1枚の関係図にしてください。矢印には何を渡すかを6文字以内で書き、個人名ではなく役割名にしてください。登場は7つまでで、多い場合は主要なものだけ図に残して、残りは図の下に並べてください。
```
双方向のやりとりがある場合は「双方向のやりとりは矢印を2本に分けてください」を追加すると、往復の非効率が見えるようになる。

### 3. フロー図（人に渡す用）
**いつ使うか**: 手順・進め方を説明する。「結局どういう順番でやるの」に答える資料が欲しいとき。
```
いまの説明を、1枚のフロー図にしてください。上から下へ、実際に手を動かす順番で並べて、1つの箱は12文字以内の短い言い切りにしてください。箱は7つまでで、例外や補足は図に入れず、図の下に3行以内で書いてください。
```
分岐（「もし◯◯なら」）は混ぜない。分岐が主役の話はパターン6（判断フローチャート）を使う。

### 4. 時系列図（自分が読む用）
**いつ使うか**: 経緯を説明する必要がある。散らばった経過を、決まったこと・変わったことだけに絞って把握したいとき。
```
経緯を1本の時間軸の図にしてください。左から右へ、日付（分かるものだけ）と出来事を並べて、出来事は12文字以内で書いてください。決まったこと・変わったことだけを置いて、検討中の話や感想は入れず、節目は7つまでにしてください。
```
日付が不明な出来事は「時期不明」として右端にまとめるよう指定すると、記憶や推測で埋めてしまう事故を防げる。

### 5. 比較表（人に渡す用）
**いつ使うか**: 選択肢を比較検討した内容を、判断材料として渡したいとき。
```
選択肢を1枚の比較表にしてください。列に選択肢、行に比べる観点を置いて、観点は判断に効くものだけ5つまでにしてください。マスの中は◯×ではなく10文字以内の事実で書き、表の下に「どれを選ぶとどうなるか」を1行ずつ添えてください。
```
◯×は主観が混じり根拠を聞かれると崩れるので必ず禁止する。観点は5つまでに絞る（多いと読まれない）。

### 6. 判断フローチャート（人に渡す用）
**いつ使うか**: 条件によって対応が変わるルール（可否判断、振り分けなど）を、迷ったときに見る1枚として共有したいとき。
```
判断のルールを1枚の分かれ道の図にしてください。ひし形の質問はすべて「はい／いいえ」の2択にして、質問は5つまで。行き着く先には、そのとき誰が何をするかを12文字以内で書いてください。
```
「場合による」を許すと図が横に膨らんで読めなくなるので、質問は必ず2択に固定する。どこにも当てはまらないケース用に「該当なし、担当に相談」の出口を1つ作っておく。

### 7. 変更前後比較（人に渡す用）
**いつ使うか**: 制度・料金・手順などを変更した際、「何が変わったか」だけを伝えたいとき。
```
変更の前と後を、左右に並べた1枚の図にしてください。変わった箇所だけを書いて、変わっていない部分は「変更なし」と1行でまとめてください。変更点ごとに追加・削除・置き換えのどれかが分かるように色を分けて、右下に変更点の数を書いてください。
```
「変わっていない部分は書かない」を明示しないと、全文を2回並べただけの図になる。件数を書かせると、相手が身構える量を事前に把握できる。

### 8. 画面ラフ（人に渡す用・合意形成用）
**いつ使うか**: フォームや画面・紙面の中身をこれから相談する。言葉だけで議論すると各自が違うものを想像してしまうとき。
```
これを、実際の画面の下書きとして1枚で見せてください。文字と枠だけの簡単な作りで、どこに何が載るか、押すと何が起きるかが分かる形にしてください。色や装飾は付けず、まだ決まっていない部分は「未定」と書いておいてください。
```
色や装飾をわざと禁止する。装飾を入れると議論が見た目の話に流れ、載せる項目や動きの合意が取れなくなる。

## 図にしない方がよい場合

以下に当てはまるときは、このスキルを使わず素直に文章で書く／答えさせる。

- **ニュアンスや温度感が本体のとき**（謝罪、断りの連絡、評価コメントなど）。図にすると事実だけが残り、気持ちが伝わらない。
- **判断の理由そのものが知りたいとき**。矢印は因果を1本に決めつけるため、条件つきの話や例外が図では表現しづらい。
- **要素が3つ以下のとき**。箇条書きで数十秒で読める内容を図にすると、絵を読み解く手間の方が大きくなる。
- **数字の根拠や計算過程を検証したいとき**。図は結論だけを残し、途中式を捨ててしまう。
- **その回答をそのまま文章として使う予定のとき**（メール本文、議事録、報告書の下書きなど）。図から書き直す二度手間になる。
- **自分がまだ内容を理解できていないとき**。図はきれいに見えるぶん「分かった気」になりやすい。理解してから図に変える方が安全。

## 図を作った後にやること

人に渡す図を作ったら、`references/post-processing.md` の整形チェックリストと、`references/failure-modes.md` のよくある崩れ方と対処を確認する。
とくに次の2つは省略しない。

1. **落ちた例外の確認**: 図にすると元の文章の「ただし」「◯◯の場合を除く」が消えやすい。人に渡す前に一度、
   `この図に入れなかった条件や例外を、図の外に箇条書きで出してください` と頼んで、落ちた分を確認する。
2. **個人情報の伏せ字化**: 社外・他部署に出す前に「名前が入っている箇所を役割名に直してください」と頼み、個人名・社名・金額を伏せる。図はスクショで一人歩きするため、毎回行う。

詳細な整形チェックリストとトラブルシューティングは以下を参照:
- `references/post-processing.md` — 人に見せる前の整形チェックリスト
- `references/failure-modes.md` — よくある崩れ方（詰め込みすぎ／ラベル崩れ／レイアウト不揃い）と対処
